# demo0 独立复核报告

审核日期：2026-09-25。对象：`F:\PROJECTS\py\qgis\demo0` 当前文件。

更新说明：以下为修复前的审核记录。0.4.0 已修复这 5 项；`test_review_repros.py` 现已改为要求正确行为的回归测试。新版验证与发布记录见 `../RELEASE-0.4.0.md`，不要把本文的旧行号及复现结果当作新版状态。

结论：已有可用的演示链路和若干有效保护，但不宜把“31 项测试通过”视为稳定交付或工程质量验收。发现 5 个可复现的边界缺陷，其中工程策略授权和数据绑定应优先修复。问题体现了开发与测试沿用同一假设的盲区；不能仅凭代码认定其由单 agent 开发造成，增加 agent 数量也不会自动消除问题。

## 调研依据与审核范围

先阅读 README 和依赖清单确定技术栈，再网络调研，随后复核代码：

- [OWASP：Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)：将动作权限与模型输出分开，限制工具能力，并在需要时要求用户批准。这是检查业务策略授权的依据，不意味着每次计算都必须重复确认。
- [LangGraph：Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)：checkpoint 保存图状态；业务对象、事件与外部副作用仍需应用自行维护一致性。文档也提示 checkpoint 持续增长需要保留策略。
- [QGIS 3.44：后台任务](https://docs.qgis.org/3.44/en/docs/pyqgis_developer_cookbook/tasks.html)：主线程对象与后台工作应分离。项目将算法放在独立进程、通过 Qt 回调加载地图的总体方向合理。

重点阅读后端全部核心模块、插件网络与会话逻辑、显示加载器、启动/停止/打包脚本、现有测试，以及 vendor 的桥接和任务一入口。未逐行审核全部 vendor 算法、第三方 GUI 库；未重跑完整 51IMB 工程或调用真实模型；未做现场规划正确性验收。业务源代码未修改，仅新增此报告和隔离复现脚本。

## 已确认问题

### 1. P1：工程策略“用户同意”由模型自己填写，缺少独立授权状态

位置：`backend/agent.py:122-127`；`backend/service.py:184-185`。

系统提示要求明确同意超 48 端口 IMB 拆分、明确选择道路，并禁止用户未要求时计算。但提交工具直接接收模型填写的 `split_oversized_imbs=true`；Service 只检查布尔值，不核对独立的用户策略确认记录。普通用户轮次始终具有提交、导出工具权限。

复现：沿用仓库 `FakeSubmitModel` 模拟错误工具调用，用户文字改为“只检查数据，不要运行，不同意拆分楼栋”，仍成功登记完整规划，拆分参数为 true。此证据证明执行边界允许错误调用，不证明真实 Qwen 在该句输入下必然越权，也不声称已完成真实提示注入攻击。

影响：一次模型误解或被不可信数据诱导，就可能修改工程假设并计算。现有 `test_agent_submission_and_export_schedule_real_async_tasks` 中，用户仅说使用正式基础设施执行，模型便额外开启拆分，测试仍认定成功，也体现测试与需求不一致。

建议：对必须由用户决定的工程策略保存项目/会话级授权记录，绑定策略及有效范围；模型只请求采用策略，服务端检查记录。已有明确授权应继承，不必每次重跑重新询问。检查模式应在工具层禁用提交/导出，而非仅写入提示词。

### 2. P1：异步登记回调可能把数据绑定到另一会话

位置：`qgis_plugin/ftth_demo0/panel.py:134-146`、`:231-244`。

`register` 与 `import_config` 传入 `self.registered_project` 作为回调，未捕获提交时的会话。登记包含 QGIS 工作进程，可能持续较长时间。返回后 `registered_project` 读取的是当前 `self.session`。

复现：在未绑定数据的会话 A 发起登记，等待期间切到另一未绑定会话 B；原回调把 A 的数据 POST 到 `/sessions/session-B/project`。已通过提取并执行原方法、使用最小网络/控件替身复现；不是完整 Qt 点击测试。

影响：B 的后续规划使用错误数据；后端禁止静默改绑的规则不会阻止第一次错绑。若返回时处于已有绑定的会话，还会把用户带回首页。

建议：请求发出时捕获 session ID 和界面请求代次，回调只更新原会话；原会话状态变化时将登记结果保留为待选择项目。用延迟响应覆盖 A→B、A→首页、A→B→A。

### 3. P2：取消与子进程创建之间存在窗口，显示取消后仍可能运算

位置：`backend/service.py:218-223`、`:338-345`。

`process` 等待 `create_subprocess_exec` 返回后才写入 `self.processes`。在等待期间，`cancel` 可以将 run 改为 cancelled，但由于进程表中没有该 ID，不会终止子进程；创建返回后也不复核 cancelled 状态。

复现：在创建调用处设置调度屏障，先请求取消，再释放屏障。真实 QGIS Python 子进程仍执行并写入临时标记文件，返回码 0；数据库状态已经 cancelled。没有执行工程算法。

影响：用户以为计算已停止，但 CPU/内存及全局计算队列仍被占用，工作目录仍产生文件。现有取消测试特意等到 ID 出现在 `service.processes` 后才取消，因此绕开此窗口。

建议：统一管理任务与子进程生命周期；登记进程后立即检查取消状态并终止，或让取消信号覆盖创建阶段。增加“创建前、创建中、已启动、结果回收”四阶段验证。

### 4. P2：助手事件和消息保存非原子，历史读取会漏回复

位置：`backend/agent.py:197-211`；`backend/app.py:71-82`；`qgis_plugin/ftth_demo0/panel.py:109-131`。

回复先通过 `store.event(..., "assistant", ...)` 提交，之后才 `store.put("message", item)`。两次提交之间，线程池中的 history 路由可以取得锁。此时 message 尚无 response，但 history cursor 已越过 assistant 事件；history 又不返回 assistant 事件供界面重建。

复现：在 assistant 事件提交后、message 保存前调用真实 history 路由函数，得到无 response 的消息和已越过回复的 cursor。后续 `events(after=cursor)` 也不含这条回复。

影响：用户恰好打开会话时，本次回复会缺失，直到再次重新打开或刷新完整历史。回复并非永久从数据库丢失。

建议：消息终态和对应事件在同一事务中提交；history 的消息快照与游标也应维持同一一致性边界。不要仅交换写入顺序，否则可能变成重复显示。

### 5. P2：重复启动会修改仍存活服务的任务状态

位置：`backend/service.py:52-65`；`backend/app.py:23-29`；`scripts/start.ps1:6`。

Service 构造时无条件把共享数据库内所有 queued/running 任务和消息标记为 interrupted，没有单实例锁或实例存活判断。通用启动脚本也不检查同数据目录已有实例。`start_qwen.ps1` 的端口检查不能覆盖通用启动、换端口或直接使用 ASGI 入口。

复现：第一个 Service 的数据库存在 running 任务；通过第二个 SQLite 连接创建第二个 Service，第一实例立即读到 interrupted。没有启动或停止用户现有后端。

影响：重复启动第二实例就会破坏活动状态。两个实例若同时运行，进程内 `asyncio.Lock` 也无法保证跨实例单任务；queued 任务可能被原执行器跳过。README 已提示避免双实例，但启动路径未执行此约束。

建议：在恢复数据库状态之前取得 data-dir 级 OS 文件锁，锁失败立即退出；或者增加实例租约/所有者，仅恢复确认为死亡实例留下的任务。

## 次要风险与验证盲区

- 长会话：`agent.ainvoke` 每轮带入 checkpoint 历史，未见摘要/裁剪；Qwen reasoning 元数据也保留在消息中。随着对话增长，成本、响应延迟和上下文超限风险增加。递归上限和 180 秒超时不能限制累计上下文体积；本次未做长会话压测。
- 数据规模：`Store.all`、会话列表和 history 多次加载全部对象/事件；登记中的复制和整文件哈希在 async 路由内同步执行，可能阻塞其他请求。日志同时保存在文件和 `chunks` 内存列表。当前小样例不能代表大工程性能。
- 业务有效性：现有 comparison 主要比较图层/线路数量，不能判断成本、接通率、容量约束、几何质量或算法最优性。代码已有“不代表质量”提示，这是正确的；后续仍需独立工程基准与验收指标。
- 验证记录：`VALIDATION.md` 同时保留 8、11、26 项通过记录，当前为 31 项。建议每次验证绑定源代码摘要、依赖锁、输入快照、运行命令和日期，避免旧验证被当作新版背书。
- 本机单用户前提：没有将跨会话接口当成多租户安全边界要求，也未将本地文件入口本身判定为远程任意文件漏洞；README 已明确令牌持有人可操作本服务。

# 主 Agent 未执行当前请求：代码与运行记录复核

日期：2026-09-26。范围：主对话、记忆、工具返回、提交授权、独立审查结论和回归测试。

## 结论

不是用户没有选择执行模式，也不是前端漏传了新消息。最新用户请求、allow_actions=true、allow_auto_repair=true 均已写入消息记录并进入 LangGraph。

直接观察到的模型偏离：它只调用 get_reviews 和 get_run，然后回答旧审查；没有调用 inspect_project、validate_inputs 或 submit_planning。

代码允许这种偏离直接结束。prompt 已有“以最后一条用户消息为准”和“不以旧结果代替新执行”的要求，但没有请求完成条件与服务端动作核对。不能声称只增加一句 prompt 就能解决。

## 发现

### P1：没有检查本轮动作是否完成

位置：backend/agent.py 的 respond（约 289–306 行）及 StopAfterSubmission。

respond 接受最后一个模型回复后直接标记消息 succeeded。这个状态表示生成结束，却没有独立的 requested_action / action_status / submitted_run_id 完成判定。StopAfterSubmission 只约束“提交之后”，完全覆盖不到“模型根本不提交”。

隔离假模型明确回答“旧结果已完成，无需提交新规划”，系统仍返回 succeeded，运行数为 0。应区分回复生成完成和本轮任务完成；执行请求未提交时只能给出有证据的阻塞或未完成状态，不能默认为正常完成。

### P1：当前任务、历史事实与完整报告缺少明确的信息边界

位置：backend/agent.py 的 get_run、get_reviews、respond；backend/model_client.py 的协议元数据处理。

普通轮次持续复用 session_id 的检查点，历史工具全文、旧回复、后台通知均保留；get_run 又返回完整嵌套运行摘要。模型拿到大量旧审查内容后偏离最新请求，与本次现象吻合，但无法从代码证明模型内部的具体因果过程。

建议将“本轮任务”作为明确、可验证的状态；模型默认获得简短的历史事实和运行摘要，按需查询详情。保留多轮记忆与真实基线 ID，不能简单清空全部历史。思考协议元数据应按服务商协议处理，不能为了缩短历史而盲目删除当前工具循环所需字段。

### P1：已保存工程策略没有进入默认参数解析

位置：backend/service.py resolve（约 199–215 行）、authorize_agent（约 120 行）。

resolve 只合并 Parameters 默认值、可选基线、显式覆盖值，没有合并已保存策略。authorize_agent 则仅检查模型启用的策略是否得到许可。结果是“已保存策略”仍需要模型手工翻译为参数，容易漏填、重复询问或产生与记录不同的选择。

隔离复现：只保存正式设施与拆分策略后，以 full 且无 overrides 校验，仍报路由来源和拆分未确认。修复需要确定并记录策略继承规则、参数来源和冲突；发现识别道路未登记时不能静默取消用户已保存的选项。

### P1：主 Agent 对自动修复资格的解释没有使用服务端判定

位置：backend/agent.py get_reviews；backend/review.py enforce、repair_patch；backend/service.py submit_repair。

实际补审参数补丁为空且无搜索失败原因。主 Agent 却将“仅枚举一个候选组合”解释为“符合自动修复条件”。真正的自动修复服务会拒绝这种建议，因此本次没有发生越界修改；错误发生在主回复的事实解释层。

应向主 Agent 返回明确的服务端修复判定与原因，模型不能从 info 类建议推导执行资格。结构化审查的 enforce 校验证据 ID 和结论下限，不等价于验证每一句自然语言解释都真实；主 Agent 再次自由改写会增加误读。

### P1：同一消息可以提交多个独立根运行

位置：backend/agent.py key / submit_planning；backend/service.py submit（约 243–276 行）。

提交幂等键包含参数哈希。相同消息、不同参数会产生不同 request_id 和 repair_root_id；服务端没有限制单次“一套流程”请求最多创建一个根运行。StopAfterSubmission 无法阻止同一模型响应中的并行工具提交，也不构成服务端额度约束。

隔离复现：同一授权消息分别使用候选路径数 5、10，创建两个根运行。该现象本次截图没有发生，是额外发现的边界缺口。若用户明确要求多个方案，应有显式的批次授权；不能用一条普通流程授权产生任意根运行与修复额度。

### P2：展示和测试掩盖了问题

- publish_review 把所有 findings 都叫“问题”，本次实际为 1 项警告、5 项说明。
- “补审成功”和“新规划未执行”是两个不同任务，不能以补审成功宣布整个用户请求闭合。
- submit_planning 写入消息的 submitted_run_id 会被 respond 最后的旧 item 快照覆盖，削弱持久化追溯；运行内 authorization 仍能追到原消息，不能说关联全部丢失。
- tests/test_agent.py 的 CompletionThenRerunModel 主动且固定地调用提交工具。它验证历史消息角色与参数继承，无法证明真实模型被旧报告吸引时，系统能纠正未执行行为。

## 建议修复顺序

1. 建立本轮结构化任务及完成条件，区分执行、查询、讨论和真实阻塞；不得仅凭“允许执行”开关或模糊关键词强行启动计算。
2. 服务端负责解析已保存策略与输入冲突，并限制一次流程请求的根运行数量；自动修复仍由现有确定性服务调度。
3. 默认只返回简短运行事实、程序校验与服务端修复判定；详情按需获取。历史完成通知不得覆盖当前任务。
4. 最终反馈绑定本轮真实动作记录，区分“已提交 / 阻塞 / 未完成”；主模型不能把没有提交描述成遵从执行请求。
5. 增加负向模型夹具：只读旧报告后结束、伪称已执行、把优化建议说成自动修复、一次响应提交多个参数方案，以及检查模式/缺策略/缺数据等合法不执行场景。

## 复现与边界

运行 `.venv\Scripts\python.exe -X utf8 audit/AGENT_CONTROL_REPRO.py` 可复现三个控制缺口。全部使用临时数据库与假模型，不调用真实模型或 QGIS 算法，不修改用户项目、会话和运行记录。

本轮只做审查和隔离复现，未修改生产逻辑、重启服务或重新运行用户规划。真实模型具体为何选择旧问题的内部原因不可验证；上述控制缺口与配置冲突已经通过代码和记录确认。
